Lantern 0.14 · from the team's research notes · 31 October 2026

What Lantern should do next

Fix three problems in the default theme, then protect the fixes with snapshot tests of the starter sites. The research notes produced 27 suggestions in all, and five are worth doing first.

First five

  1. Focus styles (#1). The default theme removes the outline from <a>, <button> and <input> and puts nothing in its place, so keyboard users lose track of where they are. Two of the six people interviewed raised it without being asked.
  2. Link contrast (#2). Four of the five bundled color schemes fail 4.5:1 for link text in at least one mode. Ember links on the light background are 2.91:1. One derived variable fixes all ten combinations.
  3. Missing alt text (#3). 38% of the images on the sampled sites have no alt text, and the build never mentions it. A build warning would catch the problem where it starts.
  4. Snapshot tests (#22). 3 starter sites × 2 modes × 5 color schemes = 30 snapshots. The CLI already has a test runner set up, so this is a small step.
  5. Single-page reference (#26). Half of the support threads ask something the docs already answer, just not where people looked. One searchable page shipped with the package would settle most of them.

Suggested order. Do #1–3 in one pass, since they all touch the default theme and its build checks. Then add the snapshot tests (#22) before changing the theme again (#4, #5, #15). After that, every theme change can be checked against the 30-snapshot baseline.

Effort: an afternoon for 1–3, about two days for 22 and 26 together. Most items below have a sketch.

Accessibility

1. Visible focus styles in the default theme

The default theme's reset sets outline: none on links, buttons and form fields and never adds a focus style back. Tabbing through a starter site shows no sign of where focus is. In the notes, one theme author said they copy the reset into every new theme, so the problem spreads past the default. A :focus-visible outline in the theme's link color fixes it for keyboard users without showing rings on mouse clicks.

Sketch 
:focus-visible {
  outline: 2px solid var(--link); /* see #2 */
  outline-offset: 2px;
}
/* and delete the outline: none line from reset.css */

From interview 2 (a keyboard-only user) · interview 5 (a theme author who copies the reset)

2. --link that meets contrast in every scheme

Links use each scheme's --brand color as text. Measured with the WCAG formula against the page background, light / dark:

Scheme Today With fix
harbor4.21 / 4.305.62 / 7.05
ember2.91 / 6.885.18 / 6.88
moss3.72 / 8.405.04 / 8.40
dusk5.10 / 3.655.10 / 6.71
slate6.02 / 7.156.02 / 7.15

Bold: below the 4.5:1 that body-size text needs.

A variable built with relative color syntax caps the lightness per mode and keeps the hue, so each scheme still looks like itself. Buttons are a separate problem: white text on the ember button is 3.40:1, and the fix there is a darker button color, not a lighter label.

Sketch 
:root {
  --link: oklch(from var(--brand) min(l, 0.52) c h);
}
@media (prefers-color-scheme: dark) {
  :root { --link: oklch(from var(--brand) max(l, 0.72) c h); }
}

a { color: var(--link); }

From the 2026 survey (eleven comments on hard-to-read links) · support thread 118 (a site failed an accessibility review)

3. Warn about images without alt text

In the 40 sites the team sampled, 38% of images had an empty or missing alt attribute. Most authors in the notes didn't know until someone told them. Lantern already parses every image while it resolves paths, so it can count the missing ones for free and print a warning at the end of the build. A setting turns it into an error for teams that want the build to fail.

Sketch 
# lantern.toml
[checks]
missing_alt = "warn"   # "off", "warn" or "error"

# build output
⚠ 3 images have no alt text
  content/posts/autumn-walk.md:14   photos/bridge.jpg
  content/posts/autumn-walk.md:22   photos/ferry.jpg
  content/about.md:8                team.png

From the site sample · interview 4 (a writer who learned about alt text from a reader)

4. Skip link and landmarks in the base layout

The base layout wraps everything in <div> elements, so screen-reader users can't jump to the main content or the navigation. Using <header>, <nav>, <main> and <footer> costs nothing, and a skip link takes one line. Themes that extend the base layout get both without changes. One person noted that the skip link must stay visible when it has focus, or sighted keyboard users never find it.

Sketch 
<body>
  <a href="#content" data-skip>Skip to content</a>
  <header>{{ partial "site-header" }}</header>
  <main id="content">{{ block "main" }}{{ end }}</main>
  <footer>{{ partial "site-footer" }}</footer>
</body>

From interview 2 · support thread 87 (asks how to add landmarks without forking the theme)

5. Set lang from the site config

Every page is rendered with <html lang="en">, whatever the site's language. Screen readers then read French or German pages with English pronunciation. The config already has a language key for date formatting, so the layout can use it. Pages with their own lang in front matter should override it.

Sketch 
<html lang="{{ page.lang | default: site.language }}">

From support thread 131 (a bilingual site) · interview 6 (a translator who maintains two sites)

Build speed

6. Cache parsed Markdown between builds

A full build of the largest site in the sample (4,200 pages) takes 41 seconds, and about 60% of that is parsing Markdown that didn't change. Keying a cache on each file's content hash lets the next build skip those files. The cache can live in the existing .lantern/ folder, which is already ignored by the starter sites.

Sketch 
# lantern.toml
[cache]
markdown = true            # on by default once it's proven
dir = ".lantern/cache"

From interview 1 (a docs team with 4,200 pages) · build timings · the Q3 retro

7. Resize images in a worker pool

Image resizing runs on one thread, so a photo-heavy site spends most of its build waiting on a single core. Moving it to a pool sized to the machine's cores cut a test build from 58 to 19 seconds on an eight-core laptop. It's a contained change, and the output is byte-for-byte the same.

From interview 3 (a photographer's portfolio) · build timings

8. Skip writes when the output hasn't changed

Lantern rewrites every file in public/ on each build, even when the content is identical. That wakes up file watchers, invalidates deploy caches and makes upload tools send the whole site again. Comparing a hash of the new output with the file on disk avoids all three. Two things to know first. The check needs the full list of output files to delete stale ones, and watch mode doesn't always have it (see C). Also, timestamps in the output, such as a "built at" footer, will defeat the check unless they're moved to one file.

Sketch 
async function writeIfChanged(path, contents) {
  const next = hash(contents);
  if (previousHashes.get(path) === next) return false;
  await fs.writeFile(path, contents);
  previousHashes.set(path, next);
  return true;
}

From support thread 64 (every deploy uploads 3,000 files)

9. Load highlighting grammars on demand

The syntax highlighter loads all 190 grammars at startup, which adds about 800 ms to every build and every dev-server restart. Most sites use three or four languages. Loading a grammar the first time a code block asks for it removes the delay, and sites with no code blocks never pay for it.

Sketch 
const loaded = new Map();

async function grammarFor(lang) {
  if (!loaded.has(lang)) loaded.set(lang, import(`./grammars/${lang}.js`));
  return loaded.get(lang);
}

From build timings · interview 1 · the Q3 retro

Content and templates

10. Accept fewer date formats in front matter

The date parser accepts nine formats, including two where 03/04 can mean March or April depending on the machine's locale. Three people in the notes had posts appear in the wrong order after moving to a new laptop. Accepting ISO dates and one long form would remove the guesswork, with a clear error for anything else.

Sketch 
date: 2026-03-04            # ISO date
date: 2026-03-04T09:30:00Z  # ISO date and time
date: 4 March 2026          # long form

From support thread 99

11. Typed front matter per section

Front matter is free-form, so a typo like tilte passes silently and the page renders without a title. Letting each content section declare the fields it expects, with types and defaults, would catch these at build time. Several people asked for it, and two had written their own checks as plugins. A schema is optional, so existing sites keep working as they are.

From interview 5 · the 2026 survey (the most requested feature)

12. Template errors that point at the line

When a template fails, the error names the compiled function and a line number in generated code. People in the notes described guessing which template was at fault. The compiler already keeps a source map, so the error can name the template file, the line and the expression, with a few lines of context.

Sketch 
✖ Template error in layouts/post.html:18
   16 |   <h1>{{ page.title }}</h1>
   17 |   <p>{{ page.date | date: "long" }}</p>
 > 18 |   {{ partial "author-card" page.autor }}
      |                            ^^^^^^^^^^
   page.autor is undefined. Did you mean page.author?

From interview 4 · support thread 52 (two hours to find a missing field)

13. Named arguments for shortcodes

Shortcodes take positional arguments, so {{< figure "a.jpg" "" "wide" >}} means nothing without the docs open. Named arguments read on their own, and they let a shortcode add options without breaking existing calls. Positional calls can keep working for a few releases with a deprecation warning.

Sketch 
{{< figure src="harbor.jpg" alt="Boats at dawn" width="wide" >}}
{{< note kind="warning" >}}This step deletes the cache.{{< /note >}}

From interview 6 · support thread 73 · the Q3 retro

14. Permalinks that survive a title change

The default permalink is built from the title, so fixing a typo in a title breaks every link to the page. Building it from the file name instead keeps URLs stable. Sites that want title-based URLs can still set the pattern, and a slug field overrides both.

Sketch 
# lantern.toml
[permalinks]
posts = "/:year/:filename/"   # was "/:year/:title/"

From support thread 41

15. Wrap long lines in code blocks

The default theme lets inline code and URLs run off the side of the page. On a phone, one long file path inside a table cell widens the whole page and adds a sideways scroll. Wrapping inline code anywhere fixes it, and anywhere also lowers the cell's minimum width, which break-word does not. Code blocks should keep their own horizontal scroll, since wrapped code is harder to read.

Sketch 
body { overflow-wrap: break-word; }
:not(pre) > code { overflow-wrap: anywhere; }

From support thread 108 (and the reply suggesting overflow-wrap: anywhere)

16. Drafts that only the dev server shows

Drafts are skipped everywhere today, so authors set draft: false to preview a post and sometimes forget to set it back. Showing drafts in the dev server, with a banner, and leaving them out of production builds matches what people expected.

Sketch 
lantern serve            # drafts shown, with a "Draft" banner
lantern build            # drafts left out
lantern build --drafts   # drafts included, for a staging site

From interview 4

Dev server

17. Keep the scroll position on reload

Live reload sends the browser back to the top of the page after every save. On a long article, the author scrolls back down each time. Saving the scroll position before the reload and restoring it afterwards takes a few lines in the injected client script.

Sketch 
socket.addEventListener("message", () => {
  sessionStorage.setItem("lantern:scroll", String(scrollY));
  location.reload();
});
const y = sessionStorage.getItem("lantern:scroll");
if (y) { scrollTo(0, Number(y)); sessionStorage.removeItem("lantern:scroll"); }

From interview 3 · interview 4 · the 2026 survey

18. Show build errors in the browser

When a rebuild fails, the dev server keeps serving the last good page and prints the error in the terminal. Most authors had the terminal hidden, so they saw an unchanged page and assumed the save hadn't happened. An overlay with the same message as the terminal, sent over the existing reload socket, makes the failure obvious. It should close itself once the next build succeeds.

Sketch 
socket.addEventListener("message", (event) => {
  const msg = JSON.parse(event.data);
  if (msg.type === "error") showOverlay(msg.file, msg.line, msg.text);
  if (msg.type === "reload") location.reload();
});

function showOverlay(file, line, text) {
  const dialog = document.createElement("dialog");
  const heading = document.createElement("h2");
  const pre = document.createElement("pre");
  heading.textContent = `${file}:${line}`;
  pre.textContent = text;
  dialog.append(heading, pre);
  document.body.append(dialog);
  dialog.showModal();
}

From interview 2 (lost ten minutes to a hidden error) · interview 6

Plugins

19. Plugin hooks named after build steps

Plugins hook in through three events: init, page and done. Anything that needs to run between reading content and rendering it has to patch internals, and four of the plugins the team reviewed did. Naming hooks after the real build steps gives those plugins a supported place to run. The old events can map onto the new ones for a release or two.

Sketch 
export default function readingTime() {
  return {
    name: "reading-time",
    afterContentLoaded(pages) {
      for (const page of pages) page.data.minutes = Math.ceil(page.words / 220);
    },
    beforeRender(page) { /* ... */ },
    afterWrite(files) { /* ... */ },
  };
}

From the plugin review · interview 5

20. Validate plugin options

A misspelled plugin option is ignored without a word, and the plugin falls back to its default. Letting each plugin export a small schema means Lantern can reject unknown keys and wrong types before the build starts, and name the plugin in the error. The same schema can generate the options table in each plugin's docs.

Sketch 
export const options = {
  wordsPerMinute: { type: "number", default: 220 },
  label:          { type: "string", default: "min read" },
};

// lantern.toml with a typo:
// ✖ reading-time: unknown option "wordsPerMinite". Did you mean "wordsPerMinute"?

From support thread 90 · the plugin review · interview 1 · the Q3 retro

Tooling and docs

22. Snapshot tests for the starter sites

The release checklist asks someone to open each starter site in light and dark mode with all five color schemes. That is 30 page views per release, and a focus-only problem like #1 is easy to miss. Rendering each combination in a headless browser and comparing screenshots automates it. Run it once more after a Tab press to capture focus styles.

Sketch 
// test/visual.test.js
import { test, expect } from "./browser.js";
const sites = ["blog", "docs", "portfolio"];
const schemes = ["harbor", "ember", "moss", "dusk", "slate"];

for (const site of sites)
  for (const mode of ["light", "dark"])
    for (const scheme of schemes)
      test(`${site} ${mode} ${scheme}`, async ({ page }) => {
        await page.goto(`/starters/${site}/?mode=${mode}&scheme=${scheme}`);
        await expect(page).toMatchScreenshot({ fullPage: true });
      });

From the Q3 retro (a broken dark mode shipped in 0.12) · the release checklist

23. Profile one large build

The timings in #6, #7 and #9 came from adding up log timestamps, which only shows the steps Lantern already logs. A CPU profile of the 4,200-page docs site would show where the rest of the 41 seconds goes, including time spent in plugins and in the template engine. It takes one run with the runtime's built-in profiler. It may only confirm what the logs say, but then you'll know.

From build timings

24. One config loader instead of three

This lookup appears in three places, with small differences:

const file = findUp(["lantern.toml", "lantern.yaml", "lantern.json"], { cwd: root });

The CLI, the dev server and the plugin loader each find and parse the config on their own, and the dev server doesn't read lantern.json at all. One shared loader, called once and passed down, fixes that and gives a single place to add validation.

From support thread 115 (settings ignored by lantern serve)

25. Check links in the release pipeline

The docs site has 23 broken internal links, most from pages renamed in 0.13. A link checker over the built docs takes under a minute and can fail the release when it finds one. Checking external links is slower and flakier, so run that weekly and report rather than fail.

From the docs audit · support thread 122 · the 2026 survey · the Q3 retro

26. Ship a single-page reference

The docs are spread over 60 pages, and search covers titles only. Half of the support threads in the notes ask about something the docs cover, usually on a page the person didn't think to open. One generated page with every config key, CLI flag, template helper and plugin hook, searchable with the browser's own find, would answer most of them. Ship it in the package as well, so lantern help --reference opens the copy that matches the installed version.

From the support summary · interview 1 · interview 6 · the docs audit

27. Keyboard pass on the theme's search

The default theme's search opens a panel when you type in the box. The results can't be reached with the arrow keys, Escape doesn't close the panel, and focus stays in the box after it closes. The interview with a keyboard-only user walked through each of these. Use that recording as the test script after any change to the search panel.

From interview 2

Also spotted

These four came up while checking the notes against the code. No note mentions them.

A. Feed dates use the build machine's time zone

The RSS and Atom feeds format dates in local time without an offset. A site built on a laptop in one time zone and on a build server in another publishes two different dates for the same post, and some feed readers show it twice. Reproduced on a fresh starter site. Format feed dates in UTC with an explicit offset. The sitemap's lastmod and the "updated" line in the default theme need the same change.

B. One config format

Lantern reads TOML, YAML and JSON configs, and the docs show examples in all three. Many of the support threads about config turn out to be format mistakes, not Lantern mistakes. Pick one format for the docs and the starters, and keep reading the others.

C. Watch mode misses files in new folders

The dev server watches the folders that existed when it started. A post saved in a new folder under content/ isn't built until the server restarts. Reproduced. Either watch the content root recursively, or rescan the folder list whenever a folder is created.

D. Pin theme versions

Themes are installed from a URL with no version, so a site can look different after a fresh clone. Recording the resolved version in a lock file, as packages already do, lets a site rebuild exactly as it was.

Already done

Several ideas from the notes are already in Lantern:

  • Clean URLs without .html and automatic redirects for moved pages (support thread 12, interview 3)
  • A dark-mode toggle that remembers the reader's choice and respects the system setting (the 2025 survey)
  • Responsive images with srcset for images in Markdown, and a global setting for reduced motion (interview 1)
  • Taxonomy pages for tags and categories without extra templates (the plugin review)

Left out: requests for a visual editor, a hosted service, comments and analytics. Those notes describe a different product, not a static-site generator.

Method

I read the team's research notes: six interview transcripts, 140 support threads, 212 survey responses and the Q3 retro. 61 notes described a concrete problem, and I checked each one against the Lantern 0.14 source. Three of the 27 suggestions, plus two extras found along the way, are defects I measured or reproduced on a fresh starter site.
