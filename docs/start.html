Getting started

Link the stylesheet, write semantic HTML, and build the page from sections with short headings. That is most of it.

Minimal page

A complete page. The viewport <meta> matters: without it, phones render the page at desktop width and zinc's small-screen rules never apply.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <title>Hello</title>
  <link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/zinc.css@0.1.0-next.0/zinc.min.css" />
</head>
<body>
  <main>
    <h1>Hello, world</h1>
    <p>No classes. <a href="https://example.com">Just markup.</a></p>
    <button>It styles itself</button>
  </main>
</body>
</html>

The body is the column: it is --width wide (42rem) plus the page padding, centred in the window. Running text wraps a little earlier, at --measure (38rem, about 75 characters); tables, entry lists and tinted blocks may use the whole column.

Page structure

zinc reads the shape of the page. This skeleton gets all of it:

<body>
  <header>
    <nav><ul><li><a href="/" aria-current="page">Home</a></li>…</ul></nav>
  </header>

  <main>
    <header>
      <p>Harbor API · Run 412 · 3 March</p>   <!-- context line -->
      <h1>Code health</h1>
      <p>Two modules need attention this week.</p>   <!-- lede -->
    </header>

    <section>
      <h2>Do next</h2>   <!-- a label in the margin on a wide screen -->
      <p>…</p>
    </section>

    <section>
      <h2>Findings</h2>
      …
    </section>
  </main>

  <footer><p>Generated 3 March</p></footer>
</body>
  • A <header> in the body that holds only a <nav> is a top bar, with room below it.
  • In the page header (body > header or main > header), a <p> before the <h1> is a small, muted line of context. The first <p> after the <h1> is the lede, set a size up in full text colour: write the one thing every reader should take away.
  • Top-level sections are the children of <main> (or of a <form> directly inside it). They are set apart by space alone, 4rem (3.25rem on a phone). Sections inside a section get 3rem.
  • A <footer> is small and muted, with a section's worth of space above it.

See it as a whole page in the page structure demo; this page is built the same way.

Section labels

From 56rem wide, when a section is a child of <main> (or of a <form> directly inside it) and its first child is an <h2>, the page gains a left margin (--rail, 11rem, plus a 3rem gap) and the heading moves into it. It shrinks to small text and stays in view while its section scrolls past. Below 56rem it is an ordinary heading.

  • Keep labels to one to three words, and put the sentence under them. A label reads like a tab, not a headline.
  • The <h2> must come first in its section. A section that opens with anything else keeps its heading in the column.
  • Use <h3> and below inside a section. Only a top-level section's <h2> becomes a label; a nested section's <h2> stays put.
  • A <nav> directly inside <main> that starts with an <h2> gets a label too, which suits a table of contents.

Cards and notes

Two elements carry emphasis, in opposite directions.

An <article> is a card

Outlined by a hairline on the white page, a lighter sheet on the beige paper. Use it for the one panel that deserves the spotlight: a top recommendation, a key finding, a small group of evidence cards.

An <aside> is a note. A tinted block pressed into the page, in smaller text. Use it for a caveat, a tip, or the one thing to remember.

Both reach past the text edge by their own padding, so the words inside them stay on the edge. Build pages from sections with headings and let tables, lists and prose sit directly in them; save cards for what stands out. If everything is a card, nothing is. Don't nest one <article> inside another.

Long tables

A table of every row is reference, not reading. Fold it into a <details> and say in the <summary> what is inside and how much:

<details>
  <summary>All 48 invoices</summary>
  <table>…</table>
</details>

The summary is a line of text with a chevron and no box. In a section on a screen 48rem or wider, the chevron hangs in the margin so the summary text stays on the edge. Code blocks, notes and cards inside a folded section still bleed like the rest.

Fonts

zinc uses the reader's own system faces, so the stylesheet is the only request. The defaults:

--font-sans: ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto,
  "Helvetica Neue", Arial, sans-serif;
--font-mono: ui-monospace, "SF Mono", SFMono-Regular, Menlo, Consolas,
  "Liberation Mono", monospace;
--font-display: var(--font-sans);   /* headings */

To use a web font, load it yourself and set the tokens on :root, after zinc. zinc uses three weights: 400, 500 and 600. It also sets <em>, <i> and <cite> in italic, which the browser slants for you unless you load the italic face too:

<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600&family=JetBrains+Mono:wght@400;500;600&display=swap" />
<style>
  :root {
    --font-sans: "Inter", ui-sans-serif, system-ui, sans-serif;
    --font-mono: "JetBrains Mono", ui-monospace, monospace;
  }
</style>

Set --font-display to give headings a face of their own.

Browser support

zinc is written for current browsers and ships no fallbacks. It relies on :has(), light-dark() and color-mix(), which together need Chrome and Edge 123, Firefox 121 or Safari 17.5 and later.

In an older browser the page still reads, but parts drop out. Every colour written with light-dark() (the accent, danger, the card outline and the code panel) is lost, so checked controls lose their fill and the focus ring can disappear. Without :has(), section labels, key figures, choice cards, toolbar fields and the beige paper set on <body> fall back to plain layout.

Some touches are progressive and simply skipped where unsupported:

  • <details> grows open and fades in only where interpolate-size and ::details-content are supported; elsewhere it snaps open.
  • A <dialog> fades and scales in with @starting-style. It fades out on close only where overlay can be transitioned; other browsers close it at once.
  • text-wrap: balance on headings, text-wrap: pretty on paragraphs and hanging-punctuation are ignored where unsupported.

With reduced motion set, every animation and transition ends at once. Hover styles apply only to fine pointers, so a tap on a phone never leaves a control stuck in its hover state, and on touch screens buttons grow to at least 2.75rem tall.
